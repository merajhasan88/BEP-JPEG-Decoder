# Benchmarks: this decoder vs. CPU decoders and other FPGA decoders

The CPU decoders were measured on 2026-10-12 on the owner's laptop (earlier runs: 2026-09-30, -10-04,
-10-05), this decoder on the owner's EP2C5 board (2026-09-30) and in cycle-exact simulation, and on a
remote Artix-7 board (fpgas.online, 2026-10-03 to -05). **Everything here is
single-image decode time with the JPEG already in memory (CPU) or already streaming into the
decoder (FPGA): the time to get the file in and the pixels out is not included.** Generated by
`bench/make_benchmarks_md.py`.

## Setup

| | |
|---|---|
| Images | the owner's 12 phone photos in `test_images/` (3120x4160 or 4160x3120, 4:2:2 with an EXIF thumbnail; adapter.jpg is one of them) and three small files made from adapter.jpg (`tb/corpus/`): `bench/run_bench.py`'s default set. Of the photos only adapter.jpg is in the published repository. Until 2026-10-12 these tables were of an earlier set of the owner's photos (4000x3000 photos of a screen, a 1944x2592 4:4:4 photo, donald.jpg); its CPU results stay in `bench/bench_2026-09-30.json` and the power-profile comparison below still uses them |
| CPU | Intel Core i7-8550U (Kaby Lake R, 4 cores / 8 threads, 1.8 GHz base, 4.0 GHz turbo), Ubuntu 22.04 |
| CPU clock | the laptop's `performance` power profile, held for the CPU runs (`BENCH_POWER_PROFILE=performance python3 run_bench.py`); average clock measured with `perf stat` during every run: 3.31-3.95 GHz (the laptop throttles), so every comparison with the FPGA uses the CPU times rescaled to a steady 3.9 GHz from each run's cycle count (column "ms at 3.9 GHz"), the CPU's best case (it assumes the time scales with the clock, as it does while memory stalls are negligible; it is not a run at 3.9 GHz - the raw times and clocks of every run are kept in the JSON results). FFmpeg's clock is that of the fastest of its trials, the one it reports (until 2026-10-10 it was its last trial's). The laptop is normally in its `power-saver` profile (~1 GHz): earlier versions of this file were measured that way without anyone noticing, which made every CPU decoder look about 4-5x slower (see "Correction" below) |
| CPU decoders | libjpeg-turbo 2.1.2 (the system library; C API, `-O2 -march=native` harness), libjpeg 9e (built by `bench/tools.py`), stb_image v2.30, Pillow 12.3.0 (which decodes with its own libjpeg-turbo 3.1.4.1), OpenCV 4.7.0 (the system libjpeg-turbo 2.1.2, `cv2.setNumThreads(1)`), FFmpeg 4.4.2 (its own mjpeg decoder, `-threads 1`, converting to RGB24 like the others), zune-jpeg 0.4.21 (Rust, run-time SIMD, built with Rust 1.99), Go 1.27.1's standard `image/jpeg` (YCbCr converted to RGBA with `image/draw`); each pinned to one core (`taskset -c 3`): one warm-up decode, then ~0.1 s batches for >= 1.5 s (at least 5); the median batch is reported, with the 10th-90th percentile of the batches. Each results file records the versions, power settings, method and the inputs' sha256 ("meta") |
| This decoder | the fast core (`FAST=1`, MCU order, RGB) at 95 MHz on the EP2C5 (`boards/ep2c5/fpga_jtag`, 4,473 of 4,608 LEs at the time, timing met at 95 MHz) and the compact core (`FAST=0`, `boards/ep2c5/fpga`, 50 MHz): clock counts of the cycle-exact simulation (`bench/bench_fpga.py`). On the board, with the decoder clock gated so that streaming time is excluded, the fast core's count equalled the simulation's on every image measured there (2026-09-30, `bench/board_jtag_95mhz.txt`: adapter.jpg and adp_64x64_q25_420 of these, marked \*, and the earlier image set) |
| Output | CPU decoders: RGB, raster order (libjpeg-turbo default and Pillow/OpenCV with smoothed chroma, `-nosmooth` and this decoder with replicated chroma: same pixels as libjpeg 9e `djpeg -nosmooth`); this decoder: RGB in MCU order (8x8 / 16x16 tiles, each pixel tagged with x, y) |
| Energy | CPU: RAPL package energy over the run / decodes (includes background package power); FPGA: PowerPlay vectorless estimate x decode time (low confidence) - neither is precise enough to compare energy closely |

Not measured: the laptop's Intel UHD 620 hardware JPEG decoder and GPU decoders (not available here).
